# Marketing Automation Workspace

Five marketing pipelines built on a three-layer architecture that separates what to do from
how it gets done. Ad creative generation, product photo ads, website visitor identification,
cold email campaigns, and a marketing analytics dashboard.

Everything here is a working system rather than a demo, with two deliberate exceptions named
in [What is real and what is mocked](#what-is-real-and-what-is-mocked).

## Why three layers

An LLM is probabilistic. Most business logic is not. Chaining probabilistic steps compounds
error fast: 90% accuracy per step is 59% success over five steps. So the deterministic work
moves into code and the agent is left to do only the thing it is actually good at, which is
deciding what to run next.

| Layer | What it is | Where it lives |
|---|---|---|
| **1. Directive** | The SOP. Goals, inputs, tools, outputs, edge cases, in plain language | `directives/` |
| **2. Orchestration** | The agent. Reads a directive, calls the right tools in the right order, handles errors | the agent session |
| **3. Execution** | Deterministic Python. API calls, data processing, file and database work | `execution/` |

The directives are the source of truth, not this README. Each one carries the verified API
contracts, the failure modes that have actually happened, and the reasoning behind decisions
that look arbitrary from the outside. Read the directive before changing anything in the
matching area.

## The five builds

| Build | What it produces | Directive | Entry point |
|---|---|---|---|
| **Ad creator** | On-brand paid-social ads from HTML templates, as a review gallery plus full-resolution PNGs | `directives/ad_creator.md` | `execution/ad_creator/generate_ad_creatives.py` |
| **Image ad creator** | Photorealistic product ads, generated by steering Gemini with a product photo plus style references | `directives/image_ad_creator.md` | `execution/image_ad_creator/generate_gemini_ad_batch.py` |
| **Visitor identification** | Anonymous site traffic turned into named, enriched leads with a drafted outreach email each | `directives/visitor_identification.md` | `execution/visitor_identification/run_visitor_pipeline.py` |
| **Cold email campaign** | A lead list enriched, one individually written email per lead, and a built Instantly campaign | `directives/cold_email_campaign.md` | `execution/cold_email/run_cold_pipeline.py` |
| **Dashboard** | A marketing analytics dashboard over five joined platform exports, with an in-page AI analyst | `directives/dashboard.md` | `execution/dashboard/build_dashboard.py` |

Each build also has a skill under `.claude/skills/`, which is the short operating summary an
agent loads. The directive is the long form.

## Setup

Python 3.10 or newer.

```bash
git clone <this repo>
cd <this repo>

python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
playwright install chromium          # the browser, which pip does not install

cp .env.example .env                 # then fill in only what the builds you run need
```

No API key is needed to run the test suites, the dashboard, or any pipeline's `--dry-run`
path. Keys are needed only where a build actually calls a vendor.

## Quickstart

Every command below is free. Nothing here calls a paid API.

```bash
# Dashboard: generate the mock platform data, then build the page.
python execution/mock_data/generate_platform_data.py
python execution/dashboard/build_dashboard.py --rebuild
# -> .tmp/dashboard/dashboard.html

# Ad creator: 6 reference ads straight from the sample input.
python execution/ad_creator/generate_ad_creatives.py \
    --input execution/ad_creator/sample_variables.json \
    --out .tmp/generated_ads/sample
# -> .tmp/generated_ads/sample/gallery.html

# Visitor identification: the whole pipeline, drafting prompts instead of paying for drafts.
python execution/visitor_identification/run_visitor_pipeline.py \
    --run-name demo --visitors 10 --fresh --dry-run --no-upload

# Cold email: inspect the prompts and the variant split without spending anything.
python execution/cold_email/build_cold_emails.py --dry-run

# Image ads: today's scene selection, without generating.
python execution/image_ad_creator/run_daily_image_ads.py --dry-run
```

## Tests

Five suites, 292 checks, no API keys or network required.

```bash
python execution/cold_email/test_pipeline.py               # seams, segmentation, spend gate
python execution/cold_email/test_cold_email.py             # copy rules, grounding, payloads
python execution/visitor_identification/test_rb2b_receiver.py
python execution/visitor_identification/test_enrichment_providers.py
python execution/dashboard/test_semantic_layer.py          # recomputes the numbers a second way
```

The dashboard suite is worth calling out. It recomputes the load-bearing figures straight
from the CSVs by a different route and asserts they agree with the semantic layer, so an
arithmetic mistake fails a test rather than quietly reaching the page.

## Spending money

Three of the builds call paid APIs. `execution/shared/spend_gate.py` sits immediately before
the first paid call in each one and behaves the same way everywhere:

| Situation | What happens |
|---|---|
| Interactive terminal, no flag | Prints the estimate and asks. Only a literal `yes` proceeds |
| Not a terminal, no flag | **Refuses and exits.** It never blocks on a prompt nothing will answer, and never reads silence as consent |
| `--yes-spend` | Proceeds, and still prints the estimate so the number is in the log |
| Under the free-pass threshold | Runs freely. A smoke test is how you avoid spending, and gating it teaches people to pass `--yes-spend` by reflex |

Both orchestrators ask once, at the top, and forward the approval to the stage that spends.
That is deliberate: they read their child's output through a pipe, so a question asked down
there would hang on something you could not see.

Parsing, segmentation, variant assignment and every `--dry-run` path sit before the gate and
stay runnable without approval.

## What is real and what is mocked

Two things are stubbed, both for the same reason: they need a paid data vendor that cannot be
included in a repo. Everything downstream of them is production code written against the real
contract.

- **Visitor identity resolution.** The site is a real Flask app, the traffic is real browser
  sessions that execute the pixel, and the webhook receiver is written against RB2B's
  documented contract. Only the "who is this person" answer is stand-in data. Going live is a
  config change and two deleted files, described in the directive.
- **Lead sourcing.** `execution/cold_email/scrape_leads.py` is a provider seam. The `csv`
  provider is wired and is what runs in practice, since most lists arrive as an export
  anyway. Apollo, Apify and Clay are documented but not implemented, and **the stubs raise
  rather than returning placeholder rows** — a scraper that invents leads is worse than one
  that fails, because the failure surfaces at send time.

Everything else runs against real APIs: enrichment, Gemini generation, Instantly campaign
creation, Google Drive delivery.

## Safety notes

- **The cold email pipeline is the only build that can mail a real person.** It creates the
  campaign **paused**. Activating it is a separate decision a human makes in the UI, and
  there is no flag in the orchestrator that starts sending. Pre-flight refuses to build a
  campaign that would mail a blank body, a blank subject, a malformed address or a duplicate.
- **`execution/visitor_identification/rb2b_config.json` ships a placeholder webhook token.**
  RB2B has no signature verification, so their documented auth is a random token in the URL.
  Rotate it before exposing the receiver anywhere public.
- **Everything in `.tmp/` is disposable** and regenerated by the script that writes it. Real
  deliverables go to Google Drive. Nothing in `.tmp/` is committed.
- **`.env`, `credentials.json` and `token.json` are gitignored** and have never been
  committed. Keep it that way.

## Layout

```
directives/          the SOPs, one per build. Source of truth.
.claude/skills/      the short operating summary an agent loads per build
execution/
  ad_creator/          HTML-template ads, PNG export, daily batch
  image_ad_creator/    Gemini product ads, scene pool, daily batch
  visitor_identification/  site + webhook receiver, enrichment, drafting, dashboard
  cold_email/          sourcing seam, enrichment, copy generation, Instantly campaign
  dashboard/           semantic layer, renderer, and the test that recomputes it
  mock_data/           the seeded generator behind the dashboard's five platform CSVs
  shared/              used by more than one area: Drive upload, brands, fonts,
                       the sales playbook, the enrichment seam, the spend gate
  _paths.py            path bootstrap; every script starts with the same two-line header
.tmp/                intermediates only, gitignored, always regenerable
```

Scripts live in area folders but still import each other as flat modules. `_paths.py` puts
every area on `sys.path`, so moving a script between areas never means rewriting the imports
that reach it. New scripts go in the area they serve and reuse that header; anything a second
area starts importing moves to `shared/`.
